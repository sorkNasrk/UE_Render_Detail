# 第 08 章参考答案：游戏线程、渲染线程、RHI 线程与 GPU

[返回第 08 章](../../chapters/08-threads-and-gpu.md) · [返回目录](../../README.md)

> 对应 UE 5.7.4，CL 51494982 的本地源码。时间算例是教学模型，未进行运行性能测量。

## 题 1：宏返回不是各层全部完成

不能无条件做出三个判断。`ENQUEUE_RENDER_COMMAND` 组织的是 CPU 渲染回调；接口返回时，回调可能尚未消费。即使回调已执行，它也可能只更新数据、构建 RDG 或记录 RHI 工作，GPU 仍未执行。

本版本可能先记录到 TLS 关联的 `FRenderCommandList`，使用主渲染线程命令管道，或在管道关闭时使用单独 TaskGraph 任务。某些上下文会直接执行；显式管道重载还可在允许条件下进入异步管道。必须看实际重载、配置与调用线程。

## 题 2：三次“执行”与 RHI 任务模式

RHI 命令列表 `Execute` 在 CPU 上重放 UE 的命令表示，把操作交给后端上下文。D3D12 `DrawIndexedInstanced` 在 CPU 上向图形命令列表记录索引绘制。队列 `ExecuteCommandLists` 则把适用的平台命令列表交给设备执行队列，但方法返回仍不等于 GPU 全部完成。

RHI 任务模式保留逻辑 RHI 工作与依赖顺序，把实际执行目标映射到工作线程，并带上相应 RHI 任务标记。`IsRunningRHIInSeparateThread` 为真可以表示与渲染侧分离的任务执行，不保证有一条永久专用物理 RHIThread。平台后端另有提交线程的可能性，也不能只用三条固定 CPU 轨道描述全部实现。

## 题 3：默认 Render Fence 不证明颜色可读

默认 Fence 的深度是 RenderThread，说明它覆盖的此前渲染侧命令与依赖已到达约定位置，不证明 GPU 已完成对应颜色计算或复制。

正确读回先确定 Q 所在资源、视图、阶段、区域与格式；安排适用的复制到 CPU 可访问的读回资源；在复制之后建立 GPU Fence；让 RHI 与 GPU 继续推进；稍后检查就绪，再按接口读取并解锁。还要保留请求与资源直到消费者用完，并记录结果属于哪一次请求。

忙等 `Poll` 可能占住需要推进提交的线程，使 Fence 迟迟无法满足，也会浪费 CPU。接口已经要求使用合适的等待方式，通常应在未完成时继续有用工作，稍后再查。GPU Fence 的完成还只覆盖其已建立的同步范围，不能推导全部队列空闲。

## 题 4：理想吞吐与输入延迟

教学条件是四阶段各有独立执行能力、每份依次通过、没有调度与显示开销：

```text
第一份最早完成：2 + 3 + 1 + 6 = 12 ms
充分填满后的理想完成间隔：max(2,3,1,6) = 6 ms
理想稳定吞吐率：1000/6 ≈ 166.7 份/秒
```

不同请求之间重叠可以改善利用率，却不会抹掉一份数据必须依次经过的阶段。真实执行还受共享 CPU 核心、设备资源、队列、依赖和同步限制，不能直接拿这个上限预测实际 FPS。

`r.OneFrameThreadLag=0` 会改变帧末线程同步策略，收紧适用的超前工作。但输入仍需采样、处理、记录与提交，GPU 仍需执行，交换链和显示器仍有自己的节奏；它不保证 GPU 等待全部完成，更不保证输入到屏幕零延迟。

## 题 5：裸指针与多层销毁

按值捕获裸指针只复制地址，不保活对象、不固定其内容，也不赋予跨线程访问许可。局部结构按值捕获也只保护结构本身；它内部的指针可能仍指向会失效或被并发修改的数据。

游戏对象停止活动、渲染侧消费分离命令、此前 GPU 访问结束是不同边界。本地 `UPrimitiveComponent` 用 DetachFence 参与销毁完成判断，`BeginReleaseResource` 可异步安排渲染资源释放，RHI 与后端还有待删除处理。应停止新访问，并按具体对象和资源契约保留到相应消费完成。

在每次更新后强制全局 Flush 可能把竞态暂时隐藏，并损失原本可用的重叠。正确做法是明确数据所有者、允许的修改时机、依赖和最终释放责任。
