# 第 01 章：从场景到像素

> **适用配置：**UE 5.7.4，Windows／D3D12／SM6，桌面延迟渲染，配置 A。关闭 Substrate、Nanite、Lumen、虚拟阴影贴图和硬件光线追踪。有关开关、重启和观察前提，见 [配置附录](../appendices/configuration.md)。
>
> **本章边界：**先建立形成像素所需的基本概念，不把一整套引擎实现压缩成几行代码。图形学算例均标为教学简化；源码入口经过静态核对；场景搭建和观察练习尚未在本机运行验证。

## 1.1 学完这一章，你应该能回答什么

看到一个被灯照亮的红色方块时，你应该能够解释：

1. 引擎保存了哪些数据，而这些数据为什么还不是图像。
2. 几何体、摄像机、材质和光源分别决定了什么。
3. GPU 如何从三角形得到屏幕上的覆盖位置，为什么还需要深度和颜色数据。
4. 材质中的红色数值为什么不等于最终显示的红色数值。
5. 一个透明物体如何与后面的不透明结果共同影响像素。

你不需要在本章记住矩阵乘法、背出所有 Render Pass，或读懂整份 `DeferredShadingRenderer.cpp`。本章只要求你能用自己的话，把“场景数据”和“最终颜色”之间缺失的环节说清楚。

### 1.1.1 前置知识

需要理解变量、数组、函数、条件判断和对象。如果你把一个三维位置写成 `position = (x, y, z)`，就已经具备开始学习所需的数学基础。

本章会用到三个词：

- **CPU（Central Processing Unit，中央处理器）**：运行游戏逻辑和大量引擎组织工作的处理器。
- **GPU（Graphics Processing Unit，图形处理器）**：擅长并行处理大量类似计算的处理器，本书主要用它完成图形与相关计算任务。
- **渲染（Rendering）**：按照某个视角，把场景描述计算为图像的过程。它既包括安排任务，也包括实际执行图像相关计算。

“GPU 负责绘图”只是职责概括。接下来要把这个概括拆成可以理解的数据处理步骤。

## 1.2 屏幕上的图像，与游戏世界中的对象不是同一种数据

假设屏幕显示一个方块。你在游戏代码中移动它，改的是位置；你给它换材质，改的是表面如何响应光；你转动相机，改的是观察方式。这些操作都不会直接写出“屏幕第 500 列、第 300 行应当是多红”。

这是理解渲染的第一个关键：**游戏世界描述的是对象和关系，图像描述的是二维位置上的颜色。** 渲染必须在这两种表示之间完成转换。

### 1.2.1 图像可以先理解为颜色数组

**像素（Pixel，Picture Element）**是二维图像网格中的一个位置。先用一个理想模型理解它：每个位置保存一个颜色。

如果图像宽 1280、高 720，就有：

```text
1280 × 720 = 921600 个像素位置
```

用程序员熟悉的写法，可以抽象为：

```cpp
// [教学简化] 表示一张图像，不是 UE 的纹理类型或内存布局。
Color image[720][1280];
Color p = image[300][500];
```

`image[300][500]` 表示第 300 行、第 500 列的位置，这里假定从 0 开始计数。它不是游戏世界中的某个永久对象：相机一动，同一个屏幕位置可能就看到了地面或背景。

实际 GPU 图像通常保存在**纹理（Texture）**资源中。纹理并不只用于给模型贴花纹；它也可以保存中间颜色、深度或其他二维数据。它有格式、尺寸、访问方式和 GPU 内存管理规则，不能把上面的普通数组当成真实实现。

### 1.2.2 RGB 是一种颜色表示，不是“红绿蓝三盏灯”的引擎对象

**RGB（Red、Green、Blue）**使用红、绿、蓝三个分量表示颜色。在本章的线性颜色算例里：

```text
(1, 0, 0)       只有红分量
(0, 1, 0)       只有绿分量
(0.5, 0.5, 0.5) 三个分量相同的中性值
```

这里的数值解释依赖所在的数据空间。材质属性、光照后的颜色、压缩纹理中的编码值和最终显示编码不能不加区分地互换。

本章计算混色时使用**线性颜色（Linear Color）**，即在该表示里按比例相加能表达相应的线性光量组合。它不是“人眼感觉亮度也按同样比例增长”。最终显示常常需要另行编码：**SDR（Standard Dynamic Range，标准动态范围）**指常规显示动态范围；**sRGB（standard RGB）**是一套常见的 RGB 颜色空间及编码约定。本书先按普通 SDR 输出理解，HDR 显示输出的不同转换留到第 20 章。第 05 章会详细区分线性计算值和显示编码值。

有些颜色资源还保存第四个分量 **Alpha（α）**。在简单透明混合中它用于描述混合权重，但不同资源里的 Alpha 可能有不同用途，不能看到四通道纹理就认定第四通道一定是不透明度。

### 1.2.3 分辨率不是整个渲染过程唯一的尺寸

**分辨率（Resolution）**指图像网格的宽和高。1280×720 是本书基础观察约定的输出尺寸。

内部场景颜色可能按不同的屏幕比例渲染；阴影贴图有自己的尺寸；半分辨率效果可能只在更小的网格上计算；最后的窗口后备缓冲也有自身尺寸。第 19 章讨论的时序超分辨率还会利用历史信息重建更高分辨率输出。

为了先隔离基础问题，本章将屏幕比例设为 100%，关闭动态分辨率。即使如此，也不能推导出“每一种中间纹理都是 1280×720”。

## 1.3 用同一个简单场景回答整本书的问题

先在脑中建立下列场景，不必马上启动编辑器。

| 场景成员 | 你会看到什么 | 它帮助我们理解什么 |
|---|---|---|
| 地面 | 承接物体与阴影的灰色平面 | 位置、遮挡、受光与阴影 |
| 红色方块 | 不透明、有棱角的物体 | 三角形、材质、法线、深度与 GBuffer |
| 金属球 | 表面反射较集中的球体 | 金属与非金属响应、粗糙度及反射来源 |
| 半透明蓝色薄片 | 覆盖方块的一部分 | 透明物体与背景颜色的组合 |
| 方向光 | 近似来自同一方向的照明 | 入射方向、直接光照与投影阴影 |
| 点光源 | 从一个位置向周围发光 | 光照范围、方向变化与距离衰减 |
| 摄像机 | 决定最终观察视角 | 世界位置如何对应屏幕位置 |

**不透明（Opaque）**意味着这个表面在本章的颜色合成模型中不透出后面的表面；**半透明（Translucent）**意味着前景和背景可能共同影响最终颜色。二者属于不同的处理情况，不能只理解为“同一个流程里把 Alpha 换一下”。

本书还固定两个观察位置：

- **P**：红色方块上没有被薄片覆盖的位置。
- **Q**：红色方块投影与蓝色薄片投影重叠的位置。

P 和 Q 是每次观察时选定的屏幕位置标签，不是锁定在物体表面的永久编号，也不是保证所有机器都位于同一个坐标的采样点。实际相机或窗口改变后，应重新确认它们看到了什么。

透明薄片使用 **Unlit（无光照）**材质提供已知的前景颜色，不模拟玻璃折射，也不接受本章灯光对其表面颜色的影响。这是为了先看清混合公式；它不能代表后续章节要讲的所有透明材质。

## 1.4 几何体：方块怎样变成 GPU 可以处理的数据

### 1.4.1 模型不等于一张图片

**网格（Mesh）**是一种描述几何形状的数据。基础光栅化路径常把表面表示为三角形集合。

一个**顶点（Vertex）**至少提供位置，还经常带有法线、切线、纹理坐标等属性。三个顶点可以组成一个三角形，但模型不一定把所有三角形的数据全部重复保存。

例如，一张矩形面片可由四个角点和两个三角形组成：

```text
顶点位置：v0、v1、v2、v3
三角形 A 的索引：0、1、2
三角形 B 的索引：0、2、3
```

**索引（Index）**相当于“去顶点列表取第几个元素”。这里两个三角形共享 `v0` 和 `v2`，因此不必为每次使用都另存一份完全相同的顶点数据。

GPU 使用的**顶点缓冲（Vertex Buffer）**保存顶点属性，**索引缓冲（Index Buffer）**保存引用关系。缓冲可以先理解成按约定格式组织的一段 GPU 可用数据。它们与稍后保存整张图像的纹理用途不同。

“一个立方体有 8 个角”不意味着模型文件里一定只有 8 个渲染顶点。相邻面的法线、纹理坐标或其他属性可能不同，同一个几何位置因此可能对应多个顶点记录。这个区别会在第 03 章再次用到。

### 1.4.2 局部形状与世界摆放需要分开

假设模型里的某个顶点是 `(50, 50, 50)`。这个位置首先可能是相对于模型自身原点定义的，称为**局部空间（Local Space）**或模型空间中的位置。

在关卡里放三个相同方块，通常不需要为每个方块重新制造一套完全不同的形状数据。可以让它们引用同一个模型，再分别提供位置、旋转和缩放。

这三个因素合称**变换（Transform）**：

- 平移决定把模型放在哪里。
- 旋转决定模型朝向哪里。
- 缩放决定模型沿各方向有多大。

应用模型到世界的变换后，得到**世界空间（World Space）**位置，也就是使用整个场景共同坐标系表示的位置。下一章会把这一步写成可计算的矩阵变换。

### 1.4.3 法线告诉我们表面朝向，不告诉我们它在哪里

**法线（Normal）**是表示表面朝向的向量，通常以垂直于表面的方向帮助计算光照。向量 `(0, 0, 1)` 可以表示朝上的方向，但不能在没有上下文时把它当成位置。

两个表面即使位于同一个附近区域，只要朝向不同，也可能受到不同程度的照明。方块朝向灯的一面与背向灯的一面亮度不同，正需要这种朝向信息。

后续会遇到几何法线、顶点插值后的法线和法线贴图扰动后的着色法线，它们不必完全相同。本章先使用“参与着色的表面朝向”这个基本含义。

### 1.4.4 UV 不是屏幕坐标

**UV（Texture Coordinates，纹理坐标）**为表面提供查找纹理数据的位置。常用字母 U、V 是为了与三维位置的 X、Y、Z 区分。

把一张图案纹理贴在方块上，需要知道方块表面的这个位置应该读取图案的哪个位置。这是 UV 的问题；方块显示到屏幕哪一列哪一行，则是相机与投影的问题。

本章材质使用常量颜色，所以暂时不需要制作贴图。但认识这个区别能避免一个常见误会：纹理分辨率、网格顶点数和屏幕分辨率是三个不同的量。

## 1.5 摄像机：同一个世界为什么会产生不同的图像

场景中每个物体都有位置，但屏幕只需要一个有限的二维观察结果。摄像机提供了将两者联系起来的观察条件。

至少要知道：摄像机在哪里、朝哪里看、采用怎样的投影方式，以及要输出多大的一张图。

### 1.5.1 透视投影表达“近大远小”

**投影（Projection）**是把三维位置映射到用于形成二维图像的坐标表示。常见的**透视投影（Perspective Projection）**使同样大小的物体在远处显得更小。

可以先把摄像机想成通过一个窗口看世界。但真实实现不是在屏幕前放一块玻璃：引擎根据相机参数建立数学变换，GPU 对顶点进行变换与后续处理。

**视场角（Field of View，FOV）**决定可见方向张开的角度。保持其他条件不变，增大视场角会看到更宽范围，原先画面里的物体通常显得更小。它不意味着物体在世界里实际缩小。

### 1.5.2 一个世界可以同时有多个观察结果

主游戏摄像机不是唯一可能需要图像的视角。编辑器视口、场景捕获、反射相关处理或阴影生成，也可能使用自己的观察或投影数据。

因此，“这一帧”需要说明是在讨论哪一种工作：整个引擎帧、一个视口的一次绘制、一个视图族，还是某个 GPU 事件范围。它们之间有关联，但不是同义词。

UE 使用 **View（视图）**表达一次观察相关的数据，使用 **ViewFamily（视图族）**组织一组相关视图与共同的渲染条件。普通单摄像机只是容易理解的一种情况。

**[源码已确认]** 游戏视口的绘制入口 `UGameViewportClient::Draw` 中构造视图族，并在满足条件时通过 Renderer 模块发起其渲染。具体位置见 [SRC-VIEWPORT](../appendices/source-index.md#src-viewport)。本章先认识这层对应关系，第 07 章再解释构造参数与分支。

## 1.6 从三角形到像素：覆盖、深度与着色是不同问题

现在已有网格和相机，仍不能直接得到完整颜色。至少还要回答三个问题：某个三角形覆盖屏幕哪里？这个位置是否被挡住？它应该贡献什么颜色或表面数据？

### 1.6.1 顶点变换先把几何体带到正确的位置

**Shader（着色器）**是为 GPU 上某种可编程处理阶段编写、编译并执行的程序。“着色”这个中文名字容易让人以为它只能计算颜色，实际上它也可以处理位置或其他数据。

基础路径中的**顶点着色器（Vertex Shader）**负责参与顶点相关计算，例如根据模型与视图的变换，把顶点送到后续阶段需要的坐标表示。材质也可能包含修改顶点位置的逻辑，因此它不总是简单地读取原始位置后直接投影。

这里没有要求 CPU 把每个顶点计算完，再逐一告诉 GPU 屏幕坐标。引擎安排数据和工作，许多逐顶点计算发生在 GPU 上。Nanite 的几何处理不能直接套用这段基础流程，见未来第 22 章。

### 1.6.2 光栅化回答覆盖问题

**光栅化（Rasterization）**把经过变换、裁剪等处理的图元转换为屏幕网格上的覆盖信息。这里的**裁剪（Clipping）**包括沿裁剪边界处理跨界图元，只保留需要的部分。对于进入光栅化的三角形，可以先想象为找出它在图像中覆盖了哪些采样位置，并为这些位置准备插值属性。

**图元（Primitive）**在这个 GPU 语境中指可被处理的基本几何单位，例如三角形。后续 UE 中的“场景 Primitive”通常对应一个更高层次的可渲染组件表示，不能据此认为一个 UE Primitive 就是一个三角形。

“覆盖了像素”还不等于“最终一定修改该像素”。还需要满足深度或**模板测试（Stencil Test）**等条件，材质也可能丢弃这个贡献。模板测试根据模板缓冲中的整数标记与设定规则限制哪些位置可以继续处理，不是 C++ 的模板编程。实际 GPU 还可能提前执行某些测试以减少无用着色，这里只是先拆分概念，不规定硬件内部测试顺序。

**像素着色器（Pixel Shader）**参与对这些片元或采样相关工作计算输出。**片元（Fragment）**可先理解成某个图元对图像某处的一次潜在贡献，它还没有保证成为最终像素颜色。同一个像素位置可能对应多个图元的片元；像素着色执行次数也不能机械地等于最终像素数。

### 1.6.3 深度回答谁被谁挡住

设屏幕某个位置同时被红方块和后面的地面覆盖。最终不透明结果通常需要保留沿该视线最近的有效表面，而不能因为地面的绘制命令恰好稍晚，就用地面覆盖方块。

**深度缓冲（Depth Buffer）**保存用于可见表面判定的深度值。**深度测试（Depth Test）**比较新的贡献与已有深度，再依据当前规则决定是否通过。

这是对可见关系的编码，不是简单地把“到相机的距离，单位米”直接写到数组里。投影、精度和深度约定都会影响数值解释。

尤其不要提前背成“数值越小一定越近”。UE 常用反向 Z 深度约定；具体比较和变换要看当前用途。第 02、03 章会说明这种选择。本章先记住：**需要在同一约定下比较，不能脱离约定解释一个深度数字。**

### 1.6.4 可见性筛选不只有一次

在真正处理所有三角形之前，可以先排除明显位于视野外的对象，这类排除不需要处理的对象或图元的工作称为**剔除（Culling）**。它与上一节沿边界截取图元的 Clipping 区分。被其他物体挡住的对象也可能通过**遮挡剔除（Occlusion Culling）**减少后续工作。

它们与每个覆盖位置上的深度测试不是同一粒度。前者可能提前减少整个对象、实例或一批几何体的工作；后者解决实际覆盖位置的可见关系。某个对象通过了早期筛选，也不意味着它的每个三角形和每个片元最终都可见。

## 1.7 材质和光源：红色表面不保证输出固定的红色

### 1.7.1 材质描述表面如何参与计算

**材质（Material）**描述表面的属性及相应计算方式，例如基础颜色、粗糙度、金属度、法线和自发光。UE 材质编辑器中的节点图是这些计算的创作表示，会参与生成和编译不同用途的 Shader。

不要把一个材质资产想成“一段在所有场合只执行一次的像素程序”。同一材质可能影响顶点位置、深度相关绘制和表面属性输出；实际 Shader 还会随平台、功能、顶点数据组织方式和 Pass 需求产生不同变体。

本章红方块采用 **Default Lit（默认受光）**材质，以便观察普通受光表面。对这个例子：

| 属性 | 先怎样理解 | 本章方块值 |
|---|---|---|
| Base Color，基础颜色 | 参与表面光学响应的颜色属性，不是已经计算好的最终像素颜色 | `(0.8, 0.05, 0.03)` |
| Metallic，金属度 | 在金属与非金属响应之间控制材质分类与相关计算 | `0` |
| Roughness，粗糙度 | 控制微表面方向分布等效应，影响高光与反射的展开程度 | `0.55` |
| Specular，镜面反射参数 | 在传统默认受光非金属材质中控制相关镜面反射强度参数 | `0.5` |

这里的 Base Color 数值按线性输入说明，不能直接拿相同十六进制 sRGB 颜色替代。粗糙度也不是把网格真正切成更多几何凹凸；后续 BRDF 章节会解释它的数学含义。

### 1.7.2 光照要结合表面位置、朝向和材料

一个红方块表面至少会受到以下因素影响：它是否处于光的作用范围；表面朝向是否面对光；中间是否有遮挡；材质如何反射光；观察方向如何影响镜面反射。

**直接光照（Direct Lighting）**表示光源直接照到表面的贡献。**间接光照（Indirect Lighting）**表示光与场景发生其他交互后再到达该表面的贡献，例如光先照到墙，再反射到方块背面。

关闭 Lumen 并不等于宇宙中不存在反射，也不等于 UE 不能计算任何间接效果。它只改变特定系统和选定配置。在本章 A 场景中，我们进一步约定不使用烘焙光照、不放置 SkyLight（天空光），以便首先隔离直接光照问题。

此时，背光区域可能很暗。金属球如果没有足够可见的反射环境，也可能大部分呈暗色，仅在直接光照或有效屏幕空间反射处出现贡献。这不能简单归因于材质失效。

### 1.7.3 阴影不是在物体背后贴一张黑图

**阴影（Shadow）**说明某些光源到表面的传播路径被遮挡。摄像机看见地面，并不保证光源也能照到地面。

常规**阴影贴图（Shadow Map）**方法会从光源相关视角记录深度等信息，之后在受光表面判断它相对于光源是否被挡住。它是另一类可见关系计算，不能用主摄像机的深度直接替代所有光源的遮挡信息。

因此，方块投下阴影并不要求它在当前主摄像机画面里完全可见；光源视角和相机视角关心的问题不同。真实 UE 还会结合范围、剔除和其他优化决定是否绘制相关阴影，第 15 章展开。

### 1.7.4 为什么金属球有助于暴露错误直觉

在传统默认受光模型中，金属表面的 Base Color 会参与其金属镜面响应；不能用“金属球的基础颜色就是漫反射颜色”去解释。粗糙度增大通常使反射和高光更分散，但不意味着材质只执行了一个模糊滤镜。

本章使用金属球是为了提出这些问题，而不是提前给出完整 BRDF。**BRDF（Bidirectional Reflectance Distribution Function，双向反射分布函数）**描述光从某个方向入射后，表面向另一个方向反射的分布关系。第 04、16 章会给出变量、几何关系与计算实例。

## 1.8 延迟渲染：先记录表面，再计算一部分光照

到这里，你可能自然想到：找到一个片元后，马上把所有光都算完并写入最终颜色。这确实是一类可能的安排，但本书主线采用**延迟渲染（Deferred Rendering）**。

这里“延迟”主要指某些光照计算被安排在表面属性记录之后，不表示这一帧固定推迟到下一帧显示，也不表示它必然比其他方法更慢。

### 1.8.1 中间结果为什么值得保存

假设像素 P 当前看到方块表面。后续多个光源可能都需要知道这个表面的朝向、粗糙度、基础颜色，以及用于确定位置的信息。

如果把可见表面的相关信息先写到屏幕对应的资源里，后续光照阶段就可以使用它们。这样把“哪个表面在这里”和“这个表面受到怎样的光”部分分开。

**GBuffer（Geometry Buffer，几何缓冲集合）**在本书传统延迟路径中指保存可见表面属性的一组缓冲或纹理。它不是一个通用 C++ 结构体，也不保证每个属性独占一张完整纹理。

**Base Pass（基础通道）**是写入这些表面信息的重要阶段，同时也可能写入场景颜色的部分贡献。不能把它简单描述为“只写 GBuffer，绝不涉及颜色”。具体输出由材质、功能和配置决定。

### 1.8.2 用一条概念记录理解 GBuffer

下面的记录只帮助你理解数据用途：

```text
[教学简化] 像素 P 对应的可见表面：
基础颜色 = (0.8, 0.05, 0.03)
粗糙度   = 0.55
金属度   = 0
表面法线 = 某个统一空间下的方向
深度     = 按当前投影约定保存的值
```

真实实现会对属性进行编码、打包，甚至从已有信息重建其他数据。例如表面位置可能结合深度与视图变换重建，而不是另存一张“每像素世界坐标图”。深度资源也不应因为列在这张概念记录中，就被认定为某张 GBuffer 颜色纹理的一个通道。

**[源码已确认]** 本地传统材质相关的 Base Pass Shader 仍存在；可以从 [SRC-BASEPASS](../appendices/source-index.md#src-basepass) 查看读取和处理材质属性的代码，再从 [SRC-SCENE-TEXTURES](../appendices/source-index.md#src-scene-textures) 看场景纹理的组织。详细通道布局留到第 14 章按配置逐项核对。

### 1.8.3 Scene Color 是当前颜色结果，不是最终屏幕的保证

**Scene Color（场景颜色）**是渲染过程中使用的场景颜色结果。在光照、合成或后处理的不同位置，它的内容和含义会变化；不要把它当作全程只存在一个永久、内容不变的数组。

**HDR（High Dynamic Range，高动态范围）**颜色允许表达超出普通归一化显示范围的值，例如某个线性颜色分量大于 1。这在光照累加中有意义，不意味着缓冲区写坏了。

UE 还可能对场景颜色使用 **Pre-Exposure（预曝光）**相关缩放来适应内部数值范围。因此，在抓帧中看到某个纹理数值时，需要先确认所处阶段和解释方式，再与材质输入比较。

本章所有手算颜色都忽略这类内部存储变换，只在已经明确的同一线性表示里计算。

## 1.9 实际跟踪像素 P：一块表面怎样贡献颜色

现在把前面各个概念连接到一起。以下是**逻辑依赖说明**，不是宣称 CPU 和 GPU 每一步都严格串行。

### 1.9.1 第一步：游戏世界提供对象和状态

方块引用一个静态网格资产和一个材质，并具有世界变换。光源提供类型、颜色、强度和空间信息。摄像机提供观察参数。

在 UE 中，**Actor（场景中的对象）**可拥有多个 **Component（组件）**。组件承载具体能力，例如静态网格组件负责与网格显示有关的数据，光源组件承载灯光设置。

**Static Mesh（静态网格）**描述一种网格资产与渲染方式，不等于这个 Actor 永远不能移动。“资产类型是静态网格”和“组件 Mobility 设置为 Static／Movable”是两件不同的事。

### 1.9.2 第二步：引擎为渲染组织合适的表示

游戏逻辑使用的对象组织方式，不必直接等同于渲染线程和 GPU 使用的数据组织方式。

**Scene Proxy（场景代理）**是理解两侧关系时的重要概念：可渲染组件为渲染侧提供相关表示，而不是要求 GPU 直接遍历游戏 Actor 并读取任意 UObject 属性。**UObject** 是 UE 对象系统的基础类型，提供对象信息、生命周期管理等能力，不是 GPU 能直接当作几何资源消费的结构。真实实现还涉及场景登记、更新和其他管理数据。

**[源码已确认]** 本地组件注册渲染状态到 Renderer 添加 Primitive 的路径见 [SRC-PRIMITIVE](../appendices/source-index.md#src-primitive)。UE 5.7 的具体实现包含批处理与组件接口等层次，不能把概念上的“组件 → 渲染表示”当作两个函数之间永远直接相邻的一次调用。

静止对象通常可以复用已经存在的渲染表示和 GPU 资源。每帧重新观察它，不意味着每帧都从磁盘重读模型，或者销毁并重建所有数据。

### 1.9.3 第三步：确定当前视图需要处理的几何体

引擎准备视图，更新需要更新的数据，并进行不同粒度的可见性处理。方块如果在视野内且未被相应筛选完全排除，就可能继续参与绘制任务。

准备绘制需要知道用哪批几何数据、哪些 Shader、什么资源与状态。**绘制命令（Draw Command）**描述一项相关绘制工作，而不是指“向屏幕发送一张方块图片”。

### 1.9.4 第四步：GPU 确定 P 的表面贡献

在基础路径中，几何体经过顶点相关处理、光栅化和深度等判定。P 处最终选中方块的一个有效不透明表面贡献。

渲染在相应阶段写入该位置的深度和表面属性。后面的地面也许曾产生候选贡献，但它不会因此成为该位置最终可见的不透明表面。

### 1.9.5 第五步：光照使用表面信息形成颜色

直接光照阶段结合光源数据、表面属性和需要的阴影信息计算贡献。不同阶段还可能加入有效的反射或其他效果。

在我们的配置 A 中，无动态 GI、无烘焙和无天空光是约束；SSR 是另一个明确保留的反射系统。**SSR（Screen Space Reflections，屏幕空间反射）**利用屏幕相关信息近似求反射，无法仅凭当前屏幕数据保证恢复所有屏幕外或被遮挡的反射内容。

此时得到的颜色仍属于渲染中的中间结果，尚未等同于最终显示编码。

### 1.9.6 第六步：后处理与输出继续改变结果

**后处理（Post Processing）**使用图像与其他已有数据进行后续处理。曝光、色调映射、部分抗锯齿和放大等工作可以在这类组织中出现，但它们不是对所有配置固定不变的一串滤镜。

**曝光（Exposure）**控制场景光量如何映射到后续可显示的亮度尺度；**色调映射（Tone Mapping）**将高动态范围场景颜色按特定映射转换到目标显示所需范围与外观。

显示输出还涉及 UI 合成、窗口后备缓冲和呈现，后面专节说明。所以，P 的最终 RGB 不应从材质的 Base Color 直接抄过来。

### 1.9.7 用表格检查 P 的数据变化

| 位置 | 现在知道什么 | 还不知道或还没完成什么 |
|---|---|---|
| 场景数据 | 方块形状、位置、材质，相机和灯光 | 它将覆盖哪些屏幕位置 |
| 可见性与几何处理 | 当前视图需要处理的几何和覆盖关系 | 尚未完成所有颜色贡献 |
| 深度与表面属性结果 | P 看到的表面及其属性 | 光照、反射与后续合成 |
| 光照相关结果 | P 的当前场景颜色 | 部分时序处理和显示映射；本例 P 没有薄片覆盖 |
| 输出相关结果 | 准备进入后续显示流程的图像 | 操作系统合成与物理屏幕实际刷新 |

这张表是帮助检查概念的依赖表，不规定每个资源只允许由一个 Pass 写入一次。

## 1.10 实际跟踪像素 Q：透明薄片为什么要读取背景

Q 的不透明背景仍是方块，但相机到方块之间多了一层蓝色薄片。若最终只保留方块颜色，会丢掉薄片；若只保留薄片颜色，就不像半透明覆盖。

### 1.10.1 先把算例的边界说清楚

下面计算采用：

- 一个简单的前景层和一个已经得到的背景颜色。
- 同一表示下的线性 RGB。
- 常规非预乘 Alpha 的“前景覆盖背景”混合模型。
- 无折射、无额外受光、无颜色空间转换、无预曝光比例变化。

这是 **[教学简化]**。它解释权重如何组合，并不宣称 UE 的每一种透明 Pass 都使用同样状态，或屏幕拾色器一定能读到下列结果。

### 1.10.2 逐个变量解释混合公式

记：

```text
C_front：前景薄片已经得到的线性 RGB 颜色
C_back ：背景在这一步已经得到的线性 RGB 颜色
α      ：前景的不透明度，范围 0 到 1
C_out  ：这一步混合后的线性 RGB 颜色

C_out = α × C_front + (1 - α) × C_back
```

这里乘法和加法分别作用于 R、G、B 分量。`α = 0` 表示本公式中完全保留背景；`α = 1` 表示完全采用前景。材质仍可能属于透明渲染路径，因此数值变为 1 不会自动把它重新分类成普通 Opaque 材质。

现在指定一组虚构但可计算的输入：

```text
C_front = (0.10, 0.60, 1.00)
C_back  = (0.80, 0.10, 0.05)
α       = 0.35
```

背景值是假定的这一步输入，不是从方块 Base Color 推导出来的，也不是本机抓帧测得的。计算为：

```text
R = 0.35 × 0.10 + 0.65 × 0.80 = 0.5550
G = 0.35 × 0.60 + 0.65 × 0.10 = 0.2750
B = 0.35 × 1.00 + 0.65 × 0.05 = 0.3825

C_out = (0.5550, 0.2750, 0.3825)
```

红分量仍然较大，因为背景方块以 0.65 的权重参与。蓝分量增加，是薄片前景贡献的结果。混合操作没有要求背景变成一个真实蓝色材质。

### 1.10.3 为什么透明物体不能直接套入单层 GBuffer 的解释

基础不透明 GBuffer 保存的是某个可见表面的属性。Q 却需要同时考虑薄片与其后面的内容。

如果粗暴地让薄片覆盖所有 GBuffer 属性，后续只按这一层算光照，就丢失了我们需要透过薄片看见的背景贡献。UE 因此拥有专门的透明处理与合成组织，不是所有透明表面都像不透明方块一样完整走普通 GBuffer 延迟光照路径。

有些透明材质受光，有些不受光；有些折射，有些只是简单混合；有些在景深处理前渲染，有些在其他位置合成。第 18 章会按分支展开。本章只讨论已经声明的简单无光照薄片。

### 1.10.4 深度与透明排序是两个相关但不同的问题

如果把薄片移到方块后方，Q 处不应仍把它当作可见前景。透明工作通常仍会利用不透明深度判断遮挡，但它是否写深度、使用何种测试和合成组织，需要看具体路径。

当存在多层透明物体时，混合顺序通常会影响结果。对两层一般颜色，先混 A 再混 B，与先混 B 再混 A 通常不相同。第 03、18 章会展示这个问题，不能用“让深度缓冲选最近一层”就完整解决一般半透明合成。

## 1.11 CPU 和 GPU 怎样合作，而不是轮流把整帧做完

我们已经按逻辑讲完 P 和 Q，但真实引擎还需要在不同执行单元之间组织工作。

### 1.11.1 线程是 CPU 侧的执行组织

**线程（Thread）**可先理解为程序中的一条执行序列。UE 的**游戏线程（Game Thread）**主要承担游戏世界逻辑等工作；**渲染线程（Render Thread）**承担渲染相关组织与处理；**RHI 线程**在相应配置下参与更底层的命令执行组织。

**RHI（Render Hardware Interface，渲染硬件接口）**是 UE 对底层图形平台提供的抽象层。本书的具体后端是 D3D12。RHI 线程依然运行在 CPU 上，它不是 GPU 的另一种称呼，也不是所有配置都必须有一个独立线程才能工作。

### 1.11.2 组织任务与执行任务不能混为一谈

**RDG（Render Dependency Graph，渲染依赖图）**用图的方式描述渲染任务与资源依赖。图中的 **Render Pass（渲染通道或渲染阶段）**是组织一项渲染相关工作的单位，可以安排绘制、计算或其他资源工作，并不必然等于一个物体的一次绘制。

在渲染代码中“添加一个 Pass”，常常是在登记工作与资源使用关系，并不表示 GPU 此刻已经执行完这个 Pass。

可以把它类比为先写出带先后依赖的任务表，再安排工作。但真实 RDG 还处理哪些结果会被使用、资源何时需要、状态与屏障、命令记录和执行等问题，不只是把函数放进一个普通列表。

**[源码已确认]** 本地 `FDeferredShadingSceneRenderer::Render` 接收 `FRDGBuilder` 并组织场景工作；主线通过 `FSceneRenderBuilder` 等调度层进入，之后调用 RDG 执行。见 [SRC-RENDERER-ENTRY](../appendices/source-index.md#src-renderer-entry)、[SRC-SCENE-BUILDER](../appendices/source-index.md#src-scene-builder)、[SRC-DEFERRED](../appendices/source-index.md#src-deferred) 和 [SRC-RDG](../appendices/source-index.md#src-rdg)。

### 1.11.3 为什么下一帧逻辑可能和当前 GPU 工作重叠

CPU 不必对每项已提交的 GPU 工作都立即停下等待。有些时候，GPU 还在执行较早提交的画面任务，CPU 已在准备后续工作。

重叠能够提高利用率，但受到数据依赖、队列、同步、缓存、帧节奏与运行设置的限制。因此不能根据一张概念图断言“游戏线程永远领先渲染线程一帧，GPU 永远再落后一帧”。

**同步（Synchronization）**用于保证相关读写和执行在需要的条件下正确发生。它并不意味着必须在每一个小步骤之间让所有设备都停下来。第 08～10 章将区分任务依赖、资源状态、命令提交与完成等待。

总览中的时序图表示这种可能的协作关系，没有测量任何持续时间。静态源码可以证明存在某个分支或提交调用，但实际重叠程度需要运行观察。

## 1.12 最后一段路：有了颜色，为何还不等于已经显示

处理得到场景图像之后，还要把它送到窗口显示所需的资源与系统中。

**后备缓冲（Back Buffer）**是交换链中的图像资源之一。**交换链（Swap Chain）**管理与窗口呈现相关的一组缓冲及其交换或呈现机制。

普通桌面路径还可能通过 **Slate（UE 的界面框架）**进行窗口与 UI 相关绘制。Slate 也可能建立自己的 RDG，所以不能把整个引擎帧说成“只调用一次 RDG Execute”。

**呈现（Present）**是向底层窗口显示系统提交呈现请求的环节。本书的 D3D12 Windows 路径最终可到达 DXGI 的交换链 Present 调用。**DXGI（DirectX Graphics Infrastructure）**负责 DirectX 与显示基础设施之间的部分交互。

**[源码已确认]** 相应连接见 [SRC-SLATE](../appendices/source-index.md#src-slate) 和 [SRC-D3D12-PRESENT](../appendices/source-index.md#src-d3d12-present)。

后处理函数返回、GPU 完成写入、调用 Present、操作系统合成以及屏幕实际扫描显示，是不同事件。呈现模式、同步设置、窗口系统和显示设备都会影响后面的时间关系。第 20 章会明确这段边界；本章不从一个函数调用就推断物理显示时刻。

## 1.13 动手观察：把同一个场景搭出来

> **[尚未验证]** 以下是依据本地版本设置和图形学机制编写的复现步骤，没有在本机新建项目或运行观察。数值是固定的教学起点，不保证所有机器出现相同截图或像素值。先完成 [配置 A](../appendices/configuration.md)，再开始本节。

### 1.13.1 准备一个不含额外照明的关卡

在你自己的 UE 5.7 项目中使用空关卡，避免模板已放置的天空光、天空、雾和后处理改变观察条件。保留本节需要的对象，不使用烘焙光照数据。

创建一个 **Post Process Volume（后处理体积）**，将 Infinite Extent（Unbound，无限范围）设为开启，使其影响整个观察区域。按照配置附录设置手动曝光，关闭本章不研究的动态分辨率、景深、运动模糊和 Bloom（泛光）等效果。

**Mobility（移动性）**是组件的一项设置，影响引擎如何处理其变换与光照等行为。本节方向光和点光源均设为 Movable（可移动），不用预先烘焙来解释阴影或照明。

### 1.13.2 创建材质

在配置 A 中，前三个材质使用 Surface（表面）域、Opaque（不透明）混合模式和 Default Lit 着色模型。用常量节点连接对应属性即可。

| 材质名 | Base Color | Metallic | Roughness | 其他 |
|---|---|---|---|---|
| `M_Lesson_Ground` | `(0.18, 0.18, 0.18)` | `0` | `0.8` | Specular `0.5` |
| `M_Lesson_Red` | `(0.8, 0.05, 0.03)` | `0` | `0.55` | Specular `0.5` |
| `M_Lesson_Metal` | `(0.7, 0.7, 0.7)` | `1` | `0.15` | 保持其他非必要项默认 |
| `M_Lesson_Overlay` | 不连接 Base Color | 不使用 | 不使用 | 见下文 |

薄片材质使用 Surface、Translucent、Unlit；开启 Two Sided（双面）。创建颜色常量 `Tint=(0.1, 0.6, 1.0)` 和标量参数 `EmissiveStrength=300`，用 Multiply（乘法）节点相乘后连接到 Emissive Color（自发光颜色）。因此该输入为 `(30, 180, 300)`。把 `0.35` 连接到 Opacity（不透明度），不连接折射相关输入。

**[教学简化／尚未验证]** 强度 `300` 是配合附录约 EV100=9.9 的固定曝光选择的观察起点，尚未做亮度实测。Unlit 表示不计算普通表面受光，不表示绕过曝光；若只输出原始 `Tint`，薄片可能很暗，主要表现为压暗背景。这个强度参数帮助观察蓝色前景的贡献，不代表一种经过测量的真实发光材料。第 1.10 节使用的是另行指定的混合阶段输入，不能把本节材质输出直接代入后声称会得到相同屏幕颜色。

这个 Emissive 输出为无光照薄片提供颜色，不意味着本章关闭 GI 后它会自动照亮地面。双面设置用于避免从另一侧观察时整张薄片因朝向被剔除；它不等于给面片增加真实厚度。自发光进入颜色与预曝光的代码入口见 [SRC-BASEPASS](../appendices/source-index.md#src-basepass)。

### 1.13.3 摆放对象

UE 编辑器常用长度单位为厘米；下表的位置单位按厘米填写。旋转按 **Pitch、Yaw、Roll** 的名称填写。普通 Transform（变换）面板若显示旋转 X、Y、Z，则对应 **X=Roll、Y=Pitch、Z=Yaw**：薄片填 `(0,90,0)`，相机填 `(0,-18,0)`，方向光填 `(0,-45,-30)`。缩放是比例，不是厘米。

使用 Engine Basic Shapes 的 Plane、Cube 和 Sphere 作为简单几何，先在自己的项目内容目录建立这些网格的副本，再为副本配置材质和 Nanite。地面与薄片可以使用 Plane 的项目副本；后续对照需要不同资产设置时再分别复制。这样每个练习都能保留自己的配置。表中尺寸依赖这些基础形状；如果改用其他资产，应按实际尺寸调整。

**[源码已确认]** 上述旋转字段与 Pitch、Yaw、Roll 的绑定见 [SRC-EDITOR-TRANSFORM](../appendices/source-index.md#src-editor-transform)。本章给定轴名称下的对应值，不依赖界面把三列以何种顺序摆放。

| 对象 | 位置 `(X,Y,Z)` | 旋转 `(Pitch,Yaw,Roll)` | 缩放 `(X,Y,Z)` | 其他设置 |
|---|---|---|---|---|
| 地面 Plane | `(0,0,0)` | `(0,0,0)` | `(10,10,1)` | 地面材质 |
| 红 Cube | `(0,-120,50)` | `(0,0,0)` | `(1,1,1)` | 红色材质，网格不启用 Nanite |
| 金属 Sphere | `(0,130,50)` | `(0,0,0)` | `(1,1,1)` | 金属材质，网格不启用 Nanite |
| 薄片 Plane | `(-120,-165,75)` | `(90,0,0)` | `(1.4,0.7,1)` | 薄片材质；关闭 Cast Shadow |
| 普通 Camera Actor | `(-600,0,250)` | `(-18,0,0)` | `(1,1,1)` | 透视，FOV `60`，宽高比 `16:9` |
| Directional Light | 位置不影响理想方向光方向 | `(-45,-30,0)` | 保持默认 | Movable，白色，强度 `3000 lux`，Dynamic Shadow Distance MovableLight 为 `2000 cm` |
| Point Light | `(-150,200,180)` | 不作为关键变量 | 保持默认 | Movable，白色，`800 lm`，衰减半径 `500 cm` |

薄片旋转后的面应近似垂直于世界 X 轴，并位于相机与方块之间，只覆盖方块投影的一部分。若所选资产原始尺寸不同，先验证这个几何关系，再调整薄片位置；练习依赖“部分覆盖”，不依赖表里数字本身的特殊意义。

点光源启用逆平方衰减，强度单位选 Lumens（流明，lm）；方向光使用 Lux（勒克斯，lx）相关强度。这两种量不能因为都是数值就直接比较。灯光数值用于提供固定起点，光度学含义会在光照章节展开。

普通 Camera 的 Post Process Blend Weight 设为 `0`，以便主要使用附录约定的全局后处理设置；在唯一 PPV 中显式覆盖 Manual、Apply Physical Camera Exposure、ISO `100`、Shutter Speed `60`、Aperture `4` 和 Exposure Compensation `0`。不要同时用另一套相机后处理覆盖曝光。也不要把换成 CineCamera 后新增的镜头和曝光控制悄悄当作相同实验。

### 1.13.4 确认实际观察的是这台相机

在编辑器里选择 Camera 并使用 Pilot（驾驶／通过该对象观察）可以先检查构图，但编辑器视口有自己的显示标记和曝光覆盖，它不自动等同于游戏视图。

要在游戏窗口观察，可以在关卡蓝图的 BeginPlay（开始运行）事件中，用 Get Player Controller 获得玩家控制器，再调用 Set View Target with Blend，把该 Camera Actor 作为 New View Target，Blend Time 设为 `0`。这只是指定视角，不要求编写新的 C++ 类。

选择 **Standalone Game（独立游戏）**作为本书固定条件的主要观察入口。在独立游戏控制台执行附录的 `r.SetRes 1280x720w`、屏幕比例与其他观察命令，核对 1280×720 的客户区域和实际视角，并确认没有被项目自己的玩家摄像机逻辑再次覆盖。窗口边框不属于游戏视口；系统显示缩放也可能影响外部截图尺寸。编辑器内运行游戏的 PIE（Play In Editor）可辅助检查逻辑，但不自动等同于本节固定的独立游戏窗口条件。

如果只使用编辑器 Pilot 观察，将结果记为“编辑器视口观察”，不要与独立窗口的 GPU 时间或像素值直接混为同一测量。

### 1.13.5 四组观察，每次只改变一个变量

| 观察 | 操作 | 应该重点看什么 | 它回答的问题 |
|---|---|---|---|
| A：相机改变 | 暂时隐藏薄片，移动或旋转相机，再恢复 | 方块材质不变，投影位置和可见面改变 | 世界对象为何不等于固定像素 |
| B：光照改变 | 固定相机，改变方向光方向，再恢复 | 方块各面受光与地面阴影发生变化 | 为什么 Base Color 不等于最终颜色 |
| C：透明权重改变 | 恢复薄片，将 Opacity 依次改为 `0`、`0.35`、`1` | Q 处前景与背景贡献的变化趋势 | Alpha 在简单混合里怎样起作用 |
| D：比较中间信息 | 在可用的 Buffer Visualization（缓冲可视化）中查看 Base Color、World Normal、Scene Depth 等，再回 Lit | 属性图与最终受光图像含义不同 | 为什么要区分表面数据和最终颜色 |

缓冲可视化是一种解释或映射后的显示结果，不保证是原始纹理字节的直接呈现。Base Color 等不透明属性视图也不保证包含薄片经过最终合成后的颜色。具体可选项目以当前配置为准。

不要在观察 D 中直接把屏幕深度灰度值读成厘米，也不要用显示拾色器数值要求复现 1.10 节的线性算例。

### 1.13.6 结果不符合预期时，按含义排查

| 现象 | 先检查什么 | 为什么 |
|---|---|---|
| 画面整体很暗或过亮 | 手动曝光是否真正生效；是否存在相机、视口或其他体积覆盖；灯光单位是否正确 | 曝光与光强会改变输出，不能直接归因于材质 |
| 金属球大部分很暗 | 是否缺少可反射环境，直接光高光是否落在当前视角，SSR 是否有有效信息 | 无天空光和动态 GI 的简化场景不会保证金属整体明亮 |
| 不见薄片 | 材质模式、Opacity、双面设置、面片朝向、是否真的在相机前 | 覆盖与剔除问题可能先于颜色混合 |
| 薄片遮住整个方块 | 基础形状尺寸、薄片位置、实际使用的相机 | 需要保留 P 和 Q 两种位置以作对照 |
| 阴影与预期不同 | Movable 设置、Cast Shadow、配置 A 是否真的关闭 VSM、是否残留其他光源 | 阴影来源和路径可能与约定不符 |
| Opacity 为 1 仍不像普通不透明材质 | Blend Mode 与 Unlit 模式 | 数值权重没有把材质改成普通 GBuffer 路径 |
| 运行画面与 Pilot 不同 | 实际 View Target、编辑器显示标记、曝光覆盖与输出尺寸 | 两种视口的条件可能不同 |

建议每组记录“改了什么、保持了什么、看到了什么、哪些只是猜测”。暂时不要求记录毫秒，也不要用任务管理器的一次 GPU 百分比推断某个 Pass 的性能。

## 1.14 带着问题进入源码，而不是从文件第一行读到最后

第一次打开引擎源码，很容易被宏、模板、任务系统和大量条件分支打断。更有效的办法是先带一个窄问题，再查入口和相邻数据。

本章建议只进行下列四次阅读，每次解决一个问题：

| 问题 | 阅读入口 | 此时只需要确认什么 |
|---|---|---|
| 游戏视图在哪里发起渲染？ | [SRC-VIEWPORT](../appendices/source-index.md#src-viewport) | 视图族的构造，以及交给 Renderer 的位置 |
| 调度怎样到达具体渲染器？ | [SRC-RENDERER-ENTRY](../appendices/source-index.md#src-renderer-entry)、[SRC-SCENE-BUILDER](../appendices/source-index.md#src-scene-builder) | 任务排队、回调、RDG 创建与执行是不同层次 |
| 延迟渲染的场景工作在哪里组织？ | [SRC-DEFERRED](../appendices/source-index.md#src-deferred) | `Render` 中存在多个阶段和条件，而非一次 GPU 绘图调用 |
| 最后怎样连到窗口呈现？ | [SRC-SLATE](../appendices/source-index.md#src-slate)、[SRC-D3D12-PRESENT](../appendices/source-index.md#src-d3d12-present) | 窗口绘制、RHI 结束视口与 DXGI Present 的连接 |

读到一个函数名之后，还要追问：它是在立即做事，还是登记将来执行的工作？运行在哪个线程？读写什么资源？调用是否位于一个条件分支里？这些问题比先背下所有子函数名更有用。

本书不会把下列概念式写法伪装成 UE 的真实调用栈：

```text
[教学简化] 理解一帧的几个问题

场景与观察数据
    → 当前视图的表面覆盖与属性
    → 光照和其他颜色贡献
    → 透明与图像处理
    → 输出与呈现
```

真实实现含有资源复用、任务调度、其他视图、历史信息和多个条件分支。总览已经提供地图；源码索引提供真实定位；后续章节会逐一把两者对上。

本章的补充阅读是 Epic 的 [PBR 材质说明](../appendices/references.md#doc-pbr)和[网格绘制管线](../appendices/references.md#doc-mesh)。先阅读前者理解属性含义，后者此时只看整体数据组织；资料附录已说明适用版本和不能直接沿用的历史示例。

## 1.15 本章回顾

游戏世界保存的是对象、几何、变换、材质、灯光和观察条件；屏幕需要的是图像位置上的结果。渲染负责连接这两种表示。

几何体决定表面形状，摄像机决定观察映射，光栅化提供覆盖相关工作，深度帮助判断遮挡，材质与光照共同形成颜色。传统延迟路径先记录可见表面的相关属性，再完成一部分光照计算。

像素 P 说明一个不透明表面如何经历这些转换；像素 Q 说明前景和背景为什么可能需要共同参与颜色。透明材质不能简单套用单层不透明 GBuffer 的解释。

CPU 组织工作，GPU 执行许多并行计算。RDG、RHI 和线程分别处在不同层次。场景颜色、后处理结果和物理屏幕显示也处在不同边界。

读到这里，你应该能指出一条解释中缺失的是“数据来源”“可见关系”“表面响应”“合成”还是“执行与呈现”，而不再把它们统称为一句“GPU 会渲染”。

## 1.16 理解检查

先写出自己的推理，再看 [第 01 章答案](../appendices/exercise-answers.md#chapter-01)。

1. 方块的 Base Color 保持不变，只旋转摄像机或灯光，最终图像为什么仍可能变化？分别说明两类变化来自哪里。
2. 同一个屏幕位置被方块和地面覆盖。顶点数据、光栅化、深度测试、GBuffer 各自解决什么问题？为什么只知道三角形覆盖这个位置还不够？
3. 在线性、非预乘 Alpha 的本章简化模型中，前景为 `(0.2, 0.4, 0.8)`，背景为 `(0.6, 0.2, 0.1)`，Alpha 为 `0.25`。求混合颜色，并说明为什么不能直接要求最终屏幕拾色得到这个值。
4. 一段渲染线程代码刚调用“添加 RDG Pass”的接口，能否据此说 GPU 已经执行完该阶段？应该区分哪些步骤？
5. 把本章薄片的 Opacity 从 `0.35` 改成 `1`，是否等于把它变成普通不透明默认受光材质？为什么？再解释为什么调用 Present 不等于屏幕已经完成刷新。
